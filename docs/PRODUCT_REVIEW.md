# Thesis Keeper 业务价值审视

审视日期：2026-08-12。审视范围：`README.md`、`docs/RELEASE_GATE.md`、领域层（`app/lib/product-domain.ts`、`app/lib/demo-domain.ts`、`app/lib/demo-store.ts`）、Provider 层（`app/providers/`）、RQData Bridge（`services/rqdata_bridge/server.py`）、git 历史。

结论：产品内核有一个真实且不俗的洞察，但仓库里几乎没有承载业务论证的材料，且有一处硬伤会让核心价值在真实场景下跑不起来。

## 总体判断

| 维度 | 现状 |
|---|---|
| 洞察质量 | 好。反后见之明这个切口真实、少人做、和实现是一致的 |
| 业务论证 | 缺失。无问题陈述、无用户定义、无竞品对比、无 SDD 三件套 |
| 用户定位 | 自相矛盾。要求专业能力，提供业余形态 |
| 场景闭环 | 断裂。核心指标规则在真实标的上恒为 `DATA_MISSING` |
| Agent 必要性 | 被低估且被误述。只有编译器接线，但"仅入口用 LLM"本身是好立场，只是没说出来 |
| 工程质量 | 明显高于业务侧。不变量、迁移、验签、Provider 抽象都比业务文档扎实得多 |

## 一、创意来源：洞察成立，但没有任何论证痕迹

仓库里唯一一句价值主张在 `docs/RELEASE_GATE.md:5`：

> 核心价值不是预测涨跌，而是让用户在信息变化时忠实面对自己当初的投资理由。

这句话有分量。它对应行为金融里真实存在、且现有工具几乎不解决的问题：投资者会事后重构自己的买入理由（后见之明偏误），会在证据转向时改口而不改仓（确认偏误加处置效应）。设计明显是围绕这个打的——不可变版本、复盘时冻结 THEN 版本、逆规则加仓必须写新反证、SHA-256 快照验签。这不是套壳，是有立场的设计。

问题在于：除了这一句，没有任何东西支撑它。

- `docs/` 下只有 `RELEASE_GATE.md` 一个文件，是验收清单，不是需求文档。
- 没有用户访谈、没有痛点量化、没有"我自己踩过什么坑"的记录。
- 上层 `CLAUDE.md` 规定非平凡任务必须交付 SDD 三件套（`doc.md` 背景/目标、`tasks.md`、`summary.md`），而这个项目没有 `.comate/specs/` 目录。三次 commit 的 message 是 `Build Thesis Keeper local MVP` / `Complete Thesis Keeper P0`，没有一个字解释为什么。

从外部看，这个项目现在是"一个实现得很干净的东西"，而不是"一个回答了某个问题的东西"。作品集场景下这一条是致命的——看的人第一句会问"你为什么做这个"，而代码库无法作答。

要补的：一页 `docs/PROBLEM.md`。最有说服力的写法是具体的失败复盘——某笔持仓，买入理由是 A，半年后 A 已经不成立但仍在持有，事后被问起时给出的理由变成了 B。有这一段，整个产品的每个不变量都自动有了来源。

## 二、目标用户：产品要求的能力和产品提供的能力，不是同一个人

仓库里没有任何用户定义。从交互契约反推它实际要求的用户：

要跑通一次建仓，用户必须写出结构化的自然语言判断，人工校正三条假设的标题和描述，让权重之和严格等于 1（`app/lib/product-domain.ts:87`），从 Catalog 里选指标，为规则设定阈值加单位加连续期数，把外部资料整理成 TEXT/JSON/CSV 导入，再逐条接受或质疑证据映射。

这是卖方分析师或买方研究员的工作流。散户不会做权重归一，也不会思考"连续两个季度"。

但产品形态又是散户的：单标的、单机本地、无持仓同步、无自选股、无推送（`docs/RELEASE_GATE.md` 明确把这些排除在 P0 外）。而真正有能力填这些字段的专业用户，已经有 Wind/Bloomberg 的 note 系统、内部投研平台、或者一张自己维护的 Excel，他们缺的不是这个记录容器。

于是形成一个夹缝：要得起这套流程的人不需要它，需要它的人填不动它。

要定的：二选一，而且会改设计。

- 选专业用户，则补多标的、组合级视图、导出到投委会材料、和研报或财务数据源对接，"可审计"才是卖点。
- 选进阶个人投资者（更符合作品集定位），则必须把录入成本压到接近零：权重归一改成滑条自动配平、指标和阈值由 LLM 从自然语言直接提议好、证据靠粘贴链接而不是构造 CSV。目前 `clarificationQuestions` 只是把模糊词原样回抛（`app/lib/product-domain.ts:200`），并没有帮用户完成这件事。

## 三、使用场景：目前只有一个演示脚本，且真实场景下核心机制无数据可用

现状是一条硬编码的时间线：虚构标的「华星智算」，T0–T6，`31% → 19% → 17%`，四条固定证据（`app/lib/demo-domain.ts:69`），健康度直接按 `currentPoint` 打分（`app/lib/demo-domain.ts:125`）。作为可复现 Demo 没问题，但它是剧本，不是使用回路。

比剧本更要紧的是两个真实场景的结构性问题。

### 触发所依赖的指标，数据链路里拿不到

这是最严重的一处。`metricCatalog.EQUITY` 提供的四个指标是 `revenue_yoy`、`net_profit_yoy`、`gross_margin`、`operating_cash_flow`（`app/lib/product-domain.ts:129`），而 `compileThesisDraft` 默认用第一个 `revenue_yoy` 生成 METRIC_RULE。但 RQData Bridge 的 `metric_series` 只实现了三个 key：`price_close`、`turnover`、`nav`，其余直接抛 `UNSUPPORTED_METRIC`（`services/rqdata_bridge/server.py:68`）。

也就是说：换成真实 A 股标的后，"收入增速连续两期低于阈值则必须复盘"这条规则永远返回 `DATA_MISSING`。而 P0 不变量又规定 `DATA_MISSING` 不得当作恶化。整个产品的心脏——确定性失效检测——在真实场景下不会跳动一次，只剩用户手工导入证据这条路。目前 Bridge 只被用于取决策时的价格快照（`app/lib/demo-store.ts:838`），基本印证了这一点。

这不是 bug，是场景闭环缺口。要么接财务数据（RQData 有 `get_financials` / `get_fundamentals`，工作量不大），要么坦率地把产品重新定位成"证据驱动"而非"指标驱动"，把 METRIC_RULE 降为可选。

### 节奏与留存

财报按季度披露，规则要求连续两期，意味着一条规则最快约半年才可能触发一次。用户在这半年里没有任何反馈却要持续录入证据。这个"投入在前、回报极晚"的曲线是这类工具死掉的常见原因，值得在设计里正面回应，比如把证据侧的即时价值做厚：每次录入就能看到某条假设的支持与削弱平衡变化。

## 四、现有方案与 agent 的必要性：目前它其实不是 agent，而这未必是坏事

仓库里没有任何竞品对比。现实中的替代方案至少有雪球或韭圈儿的组合与讨论、Notion 或飞书表格做投资日志、券商 App 自选股加条件提醒、机构内部投研笔记系统，以及最强的对手——一张 Excel 加一点自律。

必须指出一处名实不符：它现在没有 agent 行为。

`LLMModule` 声明了四个模块（`app/providers/llm/StructuredLLMProvider.ts:1`）：`THESIS_COMPILER`、`EVIDENCE_EXTRACTOR`、`RELEVANCE_JUDGE`、`REVIEW_CHALLENGER`。实际接线的只有第一个。`EVIDENCE_EXTRACTOR` 只是被写进工作流日志（`app/lib/demo-store.ts:667`、`:687`），真正判断证据影响方向的是一段中文正则（`app/lib/product-domain.ts:268`）：

```ts
if (/下降|减少|低于|风险|削弱|恶化|替代|亏损/.test(text)) return "WEAKEN";
```

`RELEVANCE_JUDGE` 和 `REVIEW_CHALLENGER` 在代码里只以联合类型的字符串存在。所以当前形态是：一次"自然语言到结构化 Schema"的编译调用，加一套确定性规则引擎，且这次调用还被 Zod 严格校验、失败重修一次、再失败回落 Fixture。

有意思的是，这恰恰可以变成最强的论证，只要换个说法。LLM 在这里唯一不可替代的就是"把人说的话翻译成可监控、可审计的规则"——这一步 Excel 做不到，正则做不到，也是散户写不出阈值的根本原因。而下游全部刻意去掉 LLM（确定性规则、不可变版本、快照验签、`DATA_MISSING` 不得推断），是为了让失效判定不可被模型幻觉污染。

这是一个真实的、可辩护的技术立场：LLM 只在入口做翻译，出口必须可审计。但现在它藏在代码里，没有任何文档说出来，反而因为三个空模块显得像"没做完"。

对比 Excel 还需要一句更硬的回答：Excel 里的判断可以随时被静默改写，而这里改不了——ACTIVE 版本不可原地修改、复盘打开时冻结 THEN 版本、快照读取时重新验签。它卖的不是记录能力，是"不可篡改"这个约束。这句话在 README 里现在没有。

## 五、差异化壁垒与"用户凭什么持续用"（补充角度）

四个角度都答完之后，最容易被追问的是这个。目前的护城河候选只有"不可篡改加无未来函数"，这是设计约束层面的差异化，不是技术壁垒，竞品想抄一周就抄了。

真正的壁垒要么来自数据（能自动喂进假设的证据流），要么来自沉淀（用户积累的历史决策与自我校准数据，用久了越难迁走）。后者已经有地基（`decision_snapshots` 加版本链），但产品里没有任何一处把它反馈给用户，比如"你过去 8 次触发复盘后有 6 次选择了 HOLD，其中 4 次事后证明假设已失效"。那才是别人抄不走的东西，也是让用户半年后还愿意打开它的理由。

## 落地成完整观点所需的四层

一个立得住的产品观点需要四层各自闭合，目前只有第三层是完整的。

| 层 | 要求 | 现状 |
|---|---|---|
| 一、问题是真的 | 一份 `docs/PROBLEM.md`，核心是具体失败案例 | 缺失。不需要代码，但没有它后三层都悬空 |
| 二、用户是确定的 | 二选一并据此改设计 | 缺失。要求专业能力却提供业余形态 |
| 三、机制是可信的 | 不可变版本、THEN 冻结、验签、`DATA_MISSING` 不推断 | 已完成，质量在业务侧之上 |
| 四、闭环是通的 | 真实标的上失效检测能真的触发 | 断裂。财务指标未接入 Bridge |

除此之外还差一句现在完全没说出来的话：LLM 只在入口做"自然语言到可监控规则"的翻译，出口全程确定性且可验签。代码里就是这么实现的，但 `LLMModule` 声明的四个模块只接了一个，剩下三个只以字符串存在，看起来像没做完而不是有意为之。把这句写进 README 首屏，同一份代码就从"半成品"变成"有立场的取舍"。

## 按性价比排序的行动项

1. 补 `revenue_yoy` 等财务指标到 Bridge（`services/rqdata_bridge/server.py`）。这是唯一一个不修就让核心价值不成立的问题，工作量不大。
2. 写 `docs/PROBLEM.md`，用一个具体的真实失败案例锚定创意来源，并明确二选一的目标用户。
3. 在 README 首屏说清 agent 边界，把现在看起来像半成品的东西讲成有意为之的取舍。
